요청에서 반영까지#

FE는 Backend 계약을 화면용 값으로 변환하며 절차 순서를 스스로 결정하지 않습니다. API는 Case와 PENDING을 저장해 접수 번호를 반환하고, 배경 판단 뒤 화면이 상태를 조회합니다.

  1. FE: 현재 입력 종류와 case_history_id 조회
  2. BE: 소유권·최신 이력·동시 제출 검증 후 접수
  3. Agent: Procedure → Info → Supervisor → Review
  4. BE: 검수 대상과 최신 상태 대조, 변경·이력 저장
  5. FE: 7종 result에 맞는 반영·질문·충돌·실패·종료 화면 표시

데이터를 두는 위치#

모델 대기 중에는 DB 커넥션을 점유하지 않습니다. 서류 분석도 최신 상태를 다시 읽고 변경분만 병합합니다.

API와 상태의 기준#

API 표·타입·요청 예제는 FastAPI OpenAPI에서 생성합니다. 이번 계약은 24개 API와 로드맵 작업 26개이며, result의 PROCEDURES_COMPLETED와 Case 완료는 구분합니다.

API 타입과 필드 ↗결과 입력 4종 ↗절차 안내 종료 ↗오류와 복구 코드 ↗

실행 한도와 배포#

한 판단의 기본 한도는 모델 호출 40회·420초·Review 재작업 2회입니다. 평균 속도나 요금 보장값이 아닙니다. BackgroundTasks는 영구 큐가 아니며 재시작 잔여 PENDING은 실패와 복구로 연결합니다. /health는 별도 DB 연결 상태와 빌드 version을 반환합니다. 운영 BE는 수동 Actions 배포와 커밋 대조를 사용합니다.

실패·재시작·배포 설명 ↗검수와 추적 범위 ↗

현재 구현과 검증의 범위#

Support Agent는 현재 Graph에서 호출하지 않고, 요청 중 웹 수집·벡터 검색 RAG·기관 자동 신청은 제공하지 않습니다. 모든 정상 결과는 Review 경계를 거치지만 모든 경로가 별도 검수 LLM을 호출하지는 않습니다. 실제 운영 1건 검증과 과거 평가는 저장소의 기록이며 이번 문서 검증 결과와 합산하지 않습니다.
