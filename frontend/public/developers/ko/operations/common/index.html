코드 기준 4188520 · 확인 2026-11-11
이해하기REST API에러 코드

배경 판단과 폴링#

Case와 PENDING 이력을 저장한 뒤 요청 커넥션을 반환합니다. 배경 작업은 입력을 읽을 때와 결과를 저장할 때만 세션을 열며 모델 대기 중에는 DB 커넥션을 점유하지 않습니다. FE는 3초 간격, 최대 10분까지 상태를 확인합니다.

복구 종류#

recovery_action_code와 retryable을 확인해 다시 판단하기·내용 보완·서비스 확인·복구 행동 없음으로 나눕니다. 서버가 NONE을 반환하면 [새 상황 알려주기]로 새 글을 입력할 수 있습니다. 다만 실패 당시 judged_version과 현재 APP_VERSION이 모두 알려져 있고 서로 다르며 허용된 입력 이력인 경우 서버가 RETRY로 안내를 바꿔 같은 저장 입력을 재판단하게 합니다. 버전 하나라도 모르면 바꾸지 않습니다. 실패 카드에는 저장된 마지막 할 일도 표시합니다. 이때 지난 질문과 선택형 답은 새 입력에 넘기지 않습니다. 같은 파일의 안전 검사 차단은 일반 업로드 재시도와 다릅니다.

코드의미
RETRY보관된 같은 입력으로 허용된 판단 재개
RESUBMIT_INPUT요청한 내용을 보완해 다시 입력
CONTACT_SUPPORT서비스 쪽 확인이 필요
NONE같은 제출의 복구 행동 없음, 새 상황 글 입력 가능

재시작과 경합#

BackgroundTasks는 내구성 큐가 아닙니다. 재시작으로 남은 PENDING은 실패 상태로 풀고 복구 경로를 제공합니다. 같은 Case 접수를 잠그고 저장 직전에 최신 사실을 대조해 늦은 판단의 덮어쓰기를 막습니다.

시연 계정 초기화#

운영자용 backend/sql/reset_member_case.sql이 추가됐습니다. 선택한 회원의 Case와 종속 이력을 지우고 회원·공유 자료는 남겨 같은 카카오 계정으로 진단부터 다시 시작할 수 있게 합니다. PENDING 이력이 있거나 회원 번호가 없으면 지우지 않습니다. 끝에 member_id와 case_id를 표시하며 case_id가 null이면 삭제된 Case가 없습니다. DB 삭제는 한 트랜잭션이지만 document_data의 서류 파일은 지우지 않습니다. 실제 계정에 실행하기 전 대상과 처리 상태를 별도로 확인해야 합니다.

현재 배포 기준#

운영 BE 배포는 develop에서 수동 GitHub Actions 버튼으로 실행하며 정한 커밋을 빌드합니다. 배포 전 작업 디렉터리 수정·진행 중 배포를 확인하고 서버 잠금으로 중복 실행을 막습니다. Compose가 해석한 fastapi의 ENVIRONMENT가 prod인지 컨테이너 생성 없이 검사하고, 실행마다 별도 백업 폴더를 만듭니다. 이미지의 GIT_SHA가 APP_VERSION으로 전달돼 /health의 version과 대조하며 짧은 해시 글자 길이 대신 같은 커밋인지 확인합니다. FE·BE·Agent·E2E 검사는 배포와 구분하고, BE·Agent는 같은 FastAPI 컨테이너로 수동 배포하며 FE는 Vercel의 GitHub 연동을 사용합니다. 최신 절차와 DB 수동 migration·백업·복원 범위는 저장소 docs/deploy.md가 기준입니다. 이번 문서 갱신은 로컬 정적 페이지 배포이며 운영 서버 배포를 새로 실행한 기록이 아닙니다.

운영 상태와 데이터#

현재 /health는 별도 DB 연결로 SELECT 1을 확인하고, 성공 시 200 status: ok, DB 오류 시 503 status: unavailable을 반환하며, 둘 다 APP_VERSION의 version(미설정 시 unknown)을 포함합니다. 연결·읽기·쓰기 제한은 각각 2초이며 앱 커넥션 풀을 쓰지 않습니다. 운영 Compose는 MySQL·FastAPI와 DB·문서 볼륨을 구성합니다. 설정이 있다는 사실과 현재 배포가 성공했다는 증거는 구분합니다.
