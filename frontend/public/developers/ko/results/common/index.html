결과 알려주기

현실에서 실행한 결과를 받아 상태와 다음 행동을 다시 검토합니다.

코드 기준 5a8d11a · 확인 2026-11-11
이해하기REST API에러 코드

이 기능이 필요한 이유#

임대인에게 물어본 답이나 실제 진행 상태는 최초 진단만으로 알 수 없습니다. 이 결과를 받아 확인된 사실을 채우고 다음 계획으로 이어갑니다.

사용 흐름#

홈의 할 일에서 실제로 물어볼 질문을 확인하고, 받은 답을 보기나 글로 전달합니다.

  1. GET /cases/results로 현재 입력 종류와 판단 번호를 확인합니다.
  2. 서버가 허용한 범위 선택·완료 버튼·진행 상태 또는 최대 2,000자의 글 중 하나를 보냅니다.
  3. 새 접수 번호로 PENDING 이후 결과를 조회합니다.
  4. 반영된 내용·추가 질문·충돌·실패를 각각 표시합니다.

선택형과 직접 입력#

원상복구 범위와 철거 여부의 선택형은 현재 행동에서 서버가 허용할 때만 사용합니다. UNKNOWN은 기존 확정값을 지우지 않습니다. PARTIAL인데 구체적인 대상이 없으면 범위를 다시 묻습니다.

할 일에 맞는 버튼 답변#

GET /cases/results의 result_input_kind는 TEXT·RESTORATION_ANSWER·ACTION_DONE·RESTORATION_STATUS입니다. ACTION_DONE은 action_done_kind에 따라 [준비했어요]·[제출했어요]·[처리 끝났어요]·[끝냈어요]로 표시합니다. [아직 …]은 서버에 완료 요청을 보내지 않고 홈으로 돌아갑니다. RESTORATION_STATUS는 NOT_STARTED·IN_PROGRESS·COMPLETED 중 하나를 받습니다. 버튼 답은 모델로 다시 해석하지 않으며 검수와 저장 검증을 거칩니다.

입력 종류전달 필드
TEXTraw_input
RESTORATION_ANSWERrestoration_answer
ACTION_DONEaction_done: true
RESTORATION_STATUSrestoration_status
한 번에 하나

네 입력 필드 중 정확히 하나와 현재 case_history_id를 보냅니다. 서버는 현재 행동·질문에 맞지 않는 버튼 답을 422로 거부합니다.

철거 준비 확인#

철거 준비를 확인했다고 보고한 뒤에는 같은 준비 확인을 반복 후보로 제시하지 않습니다. 준비를 마친 뒤 진행 중으로 확인된 작업은 새 진행 보고를 기다리고, 진행 상태가 미확인이면 [아직 시작 안 했어요 / 진행 중이에요 / 다 끝냈어요]로 확인합니다. 범위를 답한 사실만으로 준비나 작업 완료를 추정하지 않습니다. 지원사업 공고만으로 실제 철거 착수를 허용하지 않으며, 다음 행동은 확인된 조건에 따라 다시 정합니다.

반영 결과 확인#

UPDATED는 이미 서버에 반영한 결과입니다. 가게 정보 필드가 같아도 준비 확인이나 절차 진행이 바뀌면 UPDATED이며, changes 배열이 비어 있다는 이유로 NO_CHANGE로 표시하지 않습니다. [맞아요]가 저장을 승인하는 것은 아닙니다. 다르게 이해했으면 직접 적어 바로잡고, 기존값과 충돌한 사실 후보는 선택을 받을 수 있습니다.

접수와 완료

HTTP 성공과 새 이력 번호는 접수 성공입니다. 반영 완료는 별도 result 값으로 판단합니다.

마지막 절차 뒤의 응답#

PROCEDURES_COMPLETED는 등록된 절차 안내가 종료됐다는 별도 결과입니다. 다음 행동·질문을 새로 만들지 않고 홈의 종료 안내로 이동합니다. 다만 Case가 아직 진행 중이면 결과 알려주기 화면은 새 글 입력을 엽니다. 폐업 날짜처럼 로드맵에 남은 일을 알리러 온 경우이며, GET /cases의 case_history_id가 같은 판단일 때만 엽니다. UPDATED·NO_CHANGE·실패와 구분해 처리합니다.
