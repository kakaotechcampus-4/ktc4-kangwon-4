# 공고 검수와 Agent 연결

[[시작하기]] · [[지원사업/목록]]

## 수집 노트를 읽을 때

`지원사업/미검수/<공고 ID>.md`에는 실제 API 수집 필드와 공식 출처를 담습니다.
`reborn-support-discovery` 블록은 기존 `SupportNoticeCandidate`와 `EvidenceRecord`의
보존 형식입니다. 신규 DB 컬럼이나 Agent가 확정한 자격 규칙이 아닙니다.

- 요약·대상·기간은 API가 제공한 문구입니다. HTML을 텍스트로 정규화했고 전체 공고 PDF는 받지 않았습니다.
- SHA-256은 정규화 공고 데이터의 hash입니다. 첨부파일·원본 HTTP 응답 전체의 hash가 아닙니다.
- `retrieved_at`은 실제 API 수집 시각입니다. 정책 시행일·검수일·접수 상태를 나타내지 않습니다.
- 공고에 없는 조건을 채우지 않고, `freshness_status=UNKNOWN`과 미검수 상태를 유지합니다.

## 검수 완료 노트를 만드는 순서

1. 공식 상세 페이지와 첨부를 직접 읽고 수정 공고·접수 안내·적용 범위를 확인합니다.
   이전 공고와 최신 공고의 관계가 불명확하면 확인 필요로 남깁니다.
2. BE가 실제 `SUPPORT_ITEM`에서 제공한 `id`, `uuid`, `external_notice_id` 연결을 확인합니다.
   공고 ID로 임의의 양의 정수나 UUID를 만들지 않습니다. DB 신규 등록은 BE 담당입니다.
3. 기존 [지원조건 모델](../../../backend/app/agent/support_agent/models.py)의 타입과
   Case 허용 필드로 표현 가능한 조건을 사람이 검수합니다. 스키마에 없는 정보가 필요하면
   [건의 문서](../be-requests.md)에 근거·영향을 적고 협의합니다.
   문구만 보고 수치·날짜·선정 여부를 추정하지 않습니다.
4. 실제 검수자와 검수 시각, 공식 Evidence, 조건별 근거 참조를 기록합니다.
   절차 연결이 필요하면 BE의 실제 `known_steps`에 있는 코드인지 확인합니다.
5. `지원사업/검수완료/<실제 SUPPORT_ITEM.uuid>.md`에 기존 `ReviewedSupportEntry` JSON을
   **`reborn-support-entry` 블록 하나**로 기록합니다. 필요한 모든 필드·규칙은
   [Wiki 조회 계약](../support-wiki.md)과 기존 모델 정의를 따릅니다.
6. 실제 Case·BE 식별자로 Wiki 조회, 조건 비교, 필수 Review 결과를 확인한 뒤 운영에 연결합니다.
   조회 성공은 선정·지급 확정이 아닙니다. Case·판단 저장은 합의된 BE 함수가 담당합니다.

초안 수집기는 기존 노트를 덮어쓰거나 검수완료 폴더를 수정하지 않습니다.
원공고가 달라진 경우 사람이 변경 내용을 비교해 검수하며, 재수집만으로 자동 승격하지 않습니다.

## 현재 완료되지 않은 연결

이 Vault를 만든 시점에는 DB 지원사업이 0건이어서 실제 ID·UUID 매핑이 없고,
검수된 조건과 검수자도 없습니다. 따라서 `HIT → 조건 비교 → Review`까지의 A7 운영 검증은
아직 수행하지 않았습니다. 원문 링크·수집 자료를 만드는 작업부터 진행한 상태입니다.
