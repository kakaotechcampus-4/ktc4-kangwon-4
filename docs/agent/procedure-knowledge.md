# 폐업 절차 지식을 어디서 읽는가

> 소유: AI · 기준일: 2026-09-20
>
> 이 문서의 책임: 절차 정보의 출처, 갱신 방법, DB로 옮길 때 바꿀 곳.

## 1. 먼저 보는 결론

- 실제 행정 절차·담당기관·공식 출처는 [`official-closure-procedure.md`](./official-closure-procedure.md)에 정리했습니다.
- **절차조회 요청 경로는 인터넷을 쓰지 않습니다.** 사전 수집 스냅샷을 읽고 사람 검수 상태를 보존합니다.
- 공식 사이트를 받아오는 코드는 **그대로 있습니다.** 다만 별도 갱신 명령에서만 돕니다.
- 검수되지 않은 자료는 `UNKNOWN`으로 나갑니다. 그러면 정보분석이 단정하지 못하고 Review가 막습니다.
- 지금 저장소는 **JSON 파일**입니다. DB 연결 시 읽는 통로 주입을 지원하지만 실제 절차 ID·적용 조건·
  근거·검수 자료를 BE와 연결하는 작업도 필요합니다.

## 2. 왜 이렇게 바꿨나

전에는 요청이 들어올 때마다 공식 사이트 3곳을 직접 받아왔습니다. 멘토 리뷰(PR #14)에서:

> 사용자 요청이 들어왔을 때 마다 공식 문서를 fetch하는 구조는 오히려 신뢰도가 떨어질 수 있습니다.
> 공식 문서 서버가 다운되었다거나, 잦은 요청으로 본 서비스가 차단 당했을 경우 공식문서 접근이
> 불가하고, 적절한 절차를 안내할 수 없게 될 수도 있습니다. (…) MVP 때는 미리 저장된 절차만을
> 서비스하고 시간이 남으면 crawler를 구현하는 것도 좋은 생각인 것 같습니다.

지식원이 하나여야 한다는 점도 같이 짚어주셨습니다. 지금은 **요청 시점의 지식원이 하나**입니다 —
검수 상태가 보존된 사전 수집 스냅샷. 갱신 경로는 그 스냅샷을 만드는 절차이지,
판단에 쓰이는 두 번째 출처가 아닙니다. 현재 자료 3건은 아직 미검수입니다.

## 3. 요청 경로

```
Graph → StoredProcedureLookupTool → 사전 수집 스냅샷(메모리, 검수 상태 보존)
                                    └ 네트워크 호출 없음, 디스크 읽기 없음
```

스냅샷은 프로세스가 뜰 때 한 번 읽어 메모리에 둡니다. 요청 중에는 조회만 합니다.
과거 합성 입력 실측에서 절차조회가 **1밀리초**였습니다([`runtime-limits.md`](./runtime-limits.md) §2).
실제 사용자 Case나 BE 조회 지연을 측정한 값이 아닙니다.

조회어와 문서를 맞추는 규칙은 기존 공식 URL registry와 **같습니다.**
그래서 출처를 인터넷에서 스냅샷으로 옮겨도 어떤 조회어가 어떤 문서를 찾는지는 바뀌지 않습니다.

맞는 문서가 없으면 **`NO_RESULTS`로 끝냅니다.** 비슷한 걸 내놓지 않습니다.

## 4. 검수 상태가 곧 신뢰도

레코드 하나에 `reviewed_by`와 `reviewed_at`이 있습니다. 이 두 칸이 최신성을 정합니다.

| 상태 | 최신성 | 결과 |
|---|---|---|
| 검수 안 됨 (`reviewed_by`가 비어 있음) | `UNKNOWN` | 정보분석이 `UNDETERMINED`로만 판단. Review가 단정을 막음 |
| 검수됨, 유효기간 안 | `CURRENT` | 정상 사용 |
| 검수됨, 유효기간 지남 | `STALE` | 경고와 함께 나가고 확정형 판단에 못 씀 |

**사람이 읽지 않은 자료는 `CURRENT`가 될 수 없습니다.** 갱신 명령이 만든 초안은 전부
검수 안 된 상태로 나옵니다. 자동으로 받아온 내용이 저절로 신뢰도를 얻는 일은 없습니다.

`review_valid_days`는 기본 90일입니다. 지나면 자동으로 `STALE`이 됩니다.

## 5. 갱신하는 법

**요청 경로가 아닙니다.** 사람이 직접 돌립니다.

```bash
PYTHONPATH=backend backend/.venv/bin/python \
  -m app.agent.procedure_tool.refresh --out /tmp/reviewed-procedures.draft.json
```

공식 출처에서 받아 초안을 만듭니다. 그 다음이 **사람이 하는 일**입니다.

1. 레코드마다 `excerpt`를 읽습니다. 그 페이지에서 **실제 절차 본문**이 담겼는지 봅니다
2. 아니면 발췌를 고칩니다 — 받아온 본문 안의 다른 구간으로 바꿉니다.
   본문에 없는 문장을 새로 쓰면 안 됩니다
3. 맞으면 `reviewed_by`와 `reviewed_at`을 채웁니다
4. `backend/app/agent/procedure_tool/data/reviewed-procedures.ko-KR.json`에 반영합니다

### 현재 스냅샷 상태 (2026-09-20)

공식 출처 3곳에서 받았고 **발췌를 절차 본문으로 교체했습니다.** 원문에서 절차 설명이
시작·끝나는 지점을 찾아 그 구간만 남겼습니다. **새로 쓴 문장은 없습니다** — 전부 받아온
본문의 실제 부분 문자열이고, 자를 때마다 그걸 확인했습니다.

| 레코드 | 담긴 내용 | 길이 |
|---|---|---|
| `TAX_BUSINESS_CLOSURE` | 부가가치세법 제8조 휴업·폐업신고서 제출, 첨부서류, 확정신고 갈음 | 1,996자 |
| `FOOD_SERVICE_CLOSURE` | 식품위생법 제37조 폐업신고서 + 영업허가증 첨부, 세무서 송부 | 1,136자 |
| `WORKPLACE_INSURANCE_CLOSURE` | 국민연금 사업장 탈퇴 신고대상·의무자·기한·서류 | 406자 |

교체 전에는 커피전문점 건이 좌측 메뉴 목록이었고, 4대보험 건은 내용변경 신고 쪽 문장이
섞여 있었습니다. 교체 뒤 과거 합성 입력을 사용한 정보분석 6회에서 내부 재시도가 없었습니다.
더미 금지 전의 개발 기록이며 현재 실제 Case 전체 실행의 검증 결과는 아닙니다.

**아직 검수 전입니다.** `reviewed_by`가 비어 있어 최신성은 `UNKNOWN`이고, 확정형 판단에
쓰이지 않습니다. 사람이 위 내용을 읽고 맞다고 판단하면 `reviewed_by`·`reviewed_at`을 채웁니다.

남은 판단거리:

- 세무 건은 내용이 맞지만 페이지 제목이 `인터넷쇼핑몰 창업자 >` 하위입니다. 카페 사용자에게
  보여줄 제목으로 쓸지, 다른 출처를 찾을지는 사람이 정할 일입니다.

## 6. DB로 옮길 때 바꿀 곳

읽는 통로가 한 겹 분리돼 있습니다.

```
StoredProcedureLookupTool
    └ ReviewedProcedureStore (통로)
         ├ JsonFileProcedureStore   ← 지금
         └ (DB 구현)                 ← 나중
```

AI 런타임은 `build_runtime(procedure_store=...)`로 이미 로딩한 `ReviewedProcedureStore`를
받습니다. 생략할 때만 기존 JSON 저장소를 엽니다. 요구하는 것은 스냅샷 버전과 레코드 목록이며,
조회 결과의 검수 상태·근거는 동일하게 검증됩니다.

DB 조회는 BE 함수가 담당하고 AI adapter는 그 결과를 읽기 인터페이스에 맞춥니다.
이 연결 지점이 생겼다는 뜻이지 **DB adapter나 B4 시드 연결이 완료됐다는 뜻은 아닙니다.**

접속 주소가 MySQL이든 SQLite든 이 통로 위 코드는 같습니다. 중요한 건 엔진이 아니라
**테이블이 한 벌이어야 한다**는 점입니다.

선행 조건은 [`be-requests.md`](./be-requests.md) 1·2·6번입니다.
`schema_table.md` 밖의 출처 컬럼·공용 테이블을 새로 만들지 않습니다.
공용 공식 원문은 기존 파일 스냅샷으로 유지할 수 있고, 실제 Case 판단에 쓴 근거의 저장은
현재 `EVIDENCE` 구조 안에서 BE와 연결합니다. 출처가 없는 절차 metadata만으로
기한·필수서류를 확정하지 않습니다.

- 공식 출처 registry와 직접 조회(갱신 전용): `backend/app/agent/procedure_tool/tool.py`
