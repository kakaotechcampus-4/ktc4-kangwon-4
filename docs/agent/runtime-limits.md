# Agent 실행 한도와 실측 기록

> 소유: AI · 기준일: 2026-09-20
>
> 이 문서의 책임: 한 번의 실행이 **얼마나 쓰고 얼마나 걸리는지**의 단일 출처.
> 다른 문서는 숫자를 반복하지 않고 여기를 가리킵니다.

## 1. 기본값과 설정

아래는 코드 기본값이다. 실제 실행은 환경변수·CLI override를 확인하며, 과거 실측 설정과 구분한다.

| 한도 | 값 | 환경변수 | 넘으면 |
|---|---|---|---|
| 실행당 LLM 호출 총 횟수 | **40** | `AGENT_MAX_LLM_CALLS_PER_RUN` | `SAFE_FAILURE` / `LOOP_LIMIT_REACHED` |
| 실행 전체 시간 | **60초** | `AGENT_RUN_DEADLINE_SECONDS` | `SAFE_FAILURE` / `RUN_DEADLINE_EXCEEDED` |
| 호출 하나의 시간 | 45초 | `AGENT_LLM_TIMEOUT_SECONDS` | 재시도 후 실패 |

둘은 서로 다른 것을 막습니다. **호출 수는 비용을, 시간은 사용자가 기다리는 길이를** 막습니다.
하나가 다른 하나를 대신하지 못해서 둘 다 둡니다.

호출 하나의 시간은 전체 상한보다 **작아야** 합니다. 같거나 크면 호출 한 번이 전체 예산을
통째로 써버립니다. 실제로 이 저장소의 `.env`가 한동안 60초/60초였습니다.

### 어떻게 세는가

- 호출 수는 **실제 HTTP 호출**을 셉니다. 재시도도 1회로 칩니다 — 재시도에도 돈이 나가니까요.
- 실행이 시작될 때 그 실행 몫의 카운터가 새로 생깁니다. 동시에 두 요청이 들어와도 섞이지 않습니다
  (`run_scope.py`, `llm.py`의 `call_budget_scope`).
- 시간은 monotonic 기준입니다. 실행 도중 시계가 조정돼도 상한이 늘거나 줄지 않습니다.
- 남은 시간이 없으면 **예산을 쓰기 전에** 멈춥니다. 끝낼 수 없는 호출에 돈을 쓰지 않습니다.

## 2. 과거 합성 입력 실측 (2026-09-19 ~ 09-20)

아래 기록은 더미 테스트 금지 지시 이전의 개발 기록이다. 이후 재실행하지 않았으며,
실제 Case·저장 성공으로 해석하지 않는다. 실제 연결 검증은
[`live-verification.md`](./live-verification.md)를 본다.

조건: `openai/gpt-4.1-mini` 공용 + Supervisor 전용 endpoint 분리, 합성 Case fixture,
절차는 검수 스냅샷 조회. 총 8회.

### 2026-09-20 수정 이후

모델이 고를 수 있는 값을 **요청 스키마에서 닫아** provider가 그 밖을 생성하지
못하게 한 뒤 다시 측정했다. 근거 참조와 절차 단계 두 곳에 적용했다.

| 구간 | 결과 |
|---|---|
| 정보분석 단독 8회 | **8회 모두 성공.** 6회는 내부 재시도도 0번 |
| 전체 실행 6회 (상한 300초) | 성공 5 / 실패 1 |
| 전체 실행 4회 (기본 60초) | **4회 모두 성공**, 26~55초 |
| LLM 호출 | 4~8회 |

이전(수정 전) 기록과 비교하면:

| | 수정 전 | 수정 후 |
|---|---|---|
| 정보분석 단독 | 8회 중 3회 실패 | 8회 모두 성공 |
| 근거 ID 오류 | 최다 실패 원인 | **0건** |
| 전체 실행 | 재작업으로 70~75초, 60초 초과 | 22~58초, 60초 안 |

### 당시 합성 입력 실측에서 읽을 것

**당시 호출 예산 40은 남았습니다.** 해당 합성 실행에서 4~8회를 썼습니다. 재작업이 줄면서
이전(13~18회)보다도 내려갔습니다. 근거가 쌓이면 낮출 수 있습니다.

**당시 기본 설정 4회는 60초 안에 끝났습니다.** 해당 실행은 26~55초였습니다.
재작업이 도는 실행은 여전히 넘길 수 있고, 그때는 안전 실패로 끝납니다.

**당시 메모리 절차조회는 1밀리초 이하였습니다.** 실제 Case·BE 조회 지연 검증은 남았습니다.

**남은 실패는 흩어져 있습니다.** 6회 중 1회가 Review의 응답 형식 실패였습니다.
한 원인이 지배하던 상태는 아닙니다.

## 3. 다시 재는 방법

실행마다 trace에 `RUN` 이벤트가 1건 남습니다. 여기에 그 실행이 **실제로 쓴 호출 수**와
**총 소요 시간**, 종료 사유가 들어 있습니다.

구성요소별 이벤트로는 이걸 알 수 없습니다. 구성요소 한 번이 여러 번의 HTTP 호출을
덮을 수 있어서, 이벤트 수가 곧 호출 수가 아니기 때문입니다.

Langfuse credential이 설정돼 있으면 거기로 갑니다. 없으면 아무 데도 보내지 않습니다.
현재 작업은 실제 Case export가 있을 때만 Graph를 실행해 관측합니다.

### Review 관측 (A9 후속 구현)

Review 이벤트의 `status=SUCCESS`는 호출이 끝났다는 뜻이며 검수 통과와 구분합니다.
`review_verdict=PASS|REVISE`가 실제 검수 판정이고, 기존 `attempt`가 검수 회차입니다.
`RUN` 이벤트에는 다음 metadata를 추가했습니다.

| 필드 | 의미 |
|---|---|
| `review_count` | 실제 판정을 반환한 Review 수. 호출 오류는 제외 |
| `review_revise_count` | 그중 REVISE 수 |
| `rework_count` | deadline 확인 후 구성요소 호출을 시작한 재작업 라운드 수 |

같은 라운드에서 여러 구성요소를 다시 호출해도 재작업은 한 번만 셉니다.
마지막 REVISE 이후 상한으로 종료하거나 시작 전 deadline을 넘기면 추가 재작업으로 세지 않습니다.
ContextVar로 실행별 집계를 분리하고, 값이 없는 선택 필드는 Langfuse metadata에 추가하지 않습니다.
원문·근거 본문·키를 기록하지 않습니다.

반송률은 `sum(review_revise_count) / sum(review_count)`로 계산할 수 있으며 분모가 0이면
판정 없음으로 표시해야 합니다. **집계 코드만 추가됐고 실제 Case에서의 검증·대시보드는 남았습니다.**
공식 문서를 이용한 기존 LLM 호출 2건의 Langfuse 저장 성공은 새 Review 집계 검증과 다릅니다.

## 4. 값을 바꿀 때

- **근거 없이 바꾸지 않습니다.** 위 표에 회차를 추가하고 나서 바꿉니다.
- 내릴 때는 정상 요청이 막히지 않는지부터 봅니다. 재시도도 예산을 쓰기 때문에
  실패가 잦은 구간에서는 같은 요청이 예산을 더 씁니다.
- 바꾼 값은 `.env.example`과 이 문서 §1에 함께 반영합니다.

## 6. 오프라인 공고 검색 (A8)

[`support-retrieval.md`](./support-retrieval.md)의 별도 명령에 적용한다. Case Graph 호출 예산과
공유하지 않으며 이 검색 자료를 운영 자격 비교에 주입하지 않는다.

| 항목 | 상한/동작 |
|---|---|
| corpus | 미검수 노트 100개, chunk 1,000개 |
| chunk | API 필드 구간 1,200자, 겹침 120자 |
| 임베딩 요청 | 한 번에 32개, 항목당 8,000자·합계 64,000자 |
| 임베딩 네트워크 | 요청당 20초, 응답 4 MiB, 자동 재시도 없음 |
| 임베딩 client | HTTP 시도 64회까지, 실패도 차감 |
| 검색 | 공개 query 1,000자, 반환 1~10개 |
| manifest/결과 파일 | 32 MiB, 신규 파일 `0600` |
| 전체 명령 | 120초 게시 deadline. 네트워크 비동기 timeout과 동기 연산 뒤 시각 검사를 함께 적용 |

동기 Chroma·파일 I/O를 운영체제 수준에서 강제 종료하는 제한은 아니다. 동기 호출이 지연돼
제어가 돌아오면 deadline을 확인하고, 초과한 manifest·결과는 최종 이름으로 게시하지 않는다.
hard wall-clock 종료가 필요한 배치 운영은 별도 프로세스 실행 제한이 필요하다.
Case 실행 중에는 이 오프라인 명령을 호출하지 않는다.
