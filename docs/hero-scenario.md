## 1. 한 줄 소개

폐업 준비부터 제출까지, 가게 상황이 바뀔 때마다 다음 할 일 하나를 다시 계산해 주는 서비스.

## 2. 타깃 페르소나

폐업 의사는 이미 확정했지만 임대차·원상복구·철거·지원금·신고·세무를 스스로 챙겨야 하는 **1~5인 비프랜차이즈 개인 카페 사장님**(가게를 빌려 쓰는 경우).
현재 로드맵은 개인 카페만 지원합니다. 프랜차이즈 카페와 일반 음식점은 "지원 준비 중"으로 안내합니다.

## 3. 대표 Hero Case — 봄날 개인카페

> 봄날 개인카페 사장님이 버튼으로 가게 상황(빌린 가게·직원·대출·배달앱 계약, 계약서의 원상복구 조항, 폐업 날짜)을 고르면 5단계 폐업 순서가 만들어지고, 첫 할 일로 "임대인에게 원상복구 범위 확인하기"가 나온다.
> 사장님이 임대인 답변("카운터랑 싱크대는 빼고, 간판도 떼야 한대요. 바닥 타일은 그대로 둬도 된대요")을 알려주면, AI가 이해한 내용을 반영해 "이렇게 이해했어요"로 보여주고 할 일이 다시 계산된다. 다르게 이해했으면 사장님이 바로잡는다.
> 이후 점포철거비 사전 신청 → 1차 적격심사 결과 → 영업 마무리 → 철거 → 통합 폐업 신고 → 정산 서류 점검·제출 → 가게 반환 → 부가세 신고까지 같은 방식으로 이어진다.

점포철거비는 철거할 예정이면 **먼저 신청해 1차 적격심사를 받은 뒤 철거**하는 것이 공고의 기본 흐름입니다. 이미 철거했어도 신청·정산 서류를 한 번에 내는 길이 있지만, **직접 철거하면 지원 대상이 아니고 철거 전 사진·전자세금계산서·계좌이체 기록이 정산에 필요**하므로 철거 전에 챙겨야 합니다. 폐업 예정자는 정산 서류를 낼 때 폐업사실증명원을 낼 수 있어야 합니다(2026 공고 원문, §10). 카운터·싱크대를 떼면 영업을 계속할 수 없으므로 영업 마무리가 철거보다 먼저입니다.

> **확인 필요 — 로드맵 단계 순서:** v3 시안과 로드맵 코드(#132)의 5단계는 "원상복구·철거"(2단계)가 "영업 마무리·폐업 신고"(3단계)보다 앞이라, 화면에서는 철거가 먼저인 것처럼 읽힙니다. 단계 이름·순서를 바꿀지, 단계 안에서 "영업 마무리 후 철거"를 안내할지 팀 확인이 필요합니다.

실제 사례에서 반복되는 패턴은 "원상복구 범위가 처음엔 정해지지 않고, 임대인 요구가 조금씩 추가된다"입니다(2026-10-11 사례 리서치). 이 시나리오는 그 패턴을 따릅니다.

## 4. Hero Loop — 7단계

| 단계 | 시스템이 해야 할 일 |
|---|---|
| 1. 입력 | 사장님이 **버튼·체크·날짜·서류 첨부**로 상황을 알려준다. 자연어는 임대인 답변 한 곳에서만 받는다. |
| 2. 사실 추출 | 정보분석 Agent가 입력에 있는 값만 꺼내고 근거를 붙인다. 서류는 문서 Tool이 종류를 나누고 값을 꺼낸다. |
| 3. Case 인식 | 저장된 값·진행 상태로 5단계 로드맵의 각 할 일이 해당/해당 없음/확인 필요인지 정하고 Blocker를 찾는다. |
| 4. 계획 | Supervisor가 Next Action 1개와 이유를 만들고 필수 Review를 거친다. 로드맵은 이 할 일을 해당 칸에 연결해 보여준다. |
| 5. 현실 실행 | 사장님이 임대인 연락·소상공인24 신청·업체 계약·신고를 직접 한다. |
| 6. 결과 입력 | "다 알렸어요", "신청했어요" 같은 버튼, 임대인 답변으로 결과를 알려준다. 서류는 올리면 점검 결과를 바로 보여준다(Turn 3). |
| 7. 검증·재계획 | 기존 값과 다르면 사장님에게 되묻고, 확인된 결과로 계획 전체를 다시 검토한다. |

`/CLAUDE.md`의 축약된 Hero Loop("Case 생성 → Blocker 1개 판단 → Next Action 1개 제시 → 사용자 실행 → 결과 입력 → Case 상태 변경 → 재계획 → 반복")의 상세판입니다.

## 5. Turn-by-turn 워크스루

### Turn 1 — 상황 진단 → 로드맵과 첫 할 일

```
입력(버튼): 가게를 빌려 씀, 직원 있음(4대보험 가입 이력), 계약서에 원상복구 조항 있음, 폐업 시기(이번 달 안에·다음 달·아직 안 정했어요)
→ 5단계 로드맵 생성(폐업 준비 / 원상복구·철거 / 영업 마무리·폐업 신고 / 지원금 정산·가게 반환 / 세금·마무리)
→ 원상복구 범위 = 모름
→ Next Action: "임대인에게 원상복구 범위와 철거 필요 여부를 확인하세요."
→ 화면: "임대인에게 이 두 가지만 물어보세요" 질문 목록
```

### Turn 2 — 임대인 답변 → AI 이해 확인 → 재계획 (시연 핵심)

```
입력: 원상복구 범위(전부 / 일부 / 불필요 / 모름)와 철거 필요 여부(필요 / 불필요 / 모름)를 고르거나 직접 쓰기
직접 쓴 예: "카운터랑 싱크대는 빼고, 간판도 떼야 한대요. 바닥 타일은 그대로 둬도 된대요."
→ 선택형: 고른 값을 그대로 검사·전달. 직접 쓴 글: 정보분석 Agent가 문장에 있는 값만 꺼냄
→ 일부인데 구체적인 내용이 없으면 그 내용을 먼저 질문. 이미 확인한 내용이 있으면 같은 질문을 반복하지 않음
→ 화면: "이렇게 이해하고 반영했어요" → 사장님이 [맞아요 / 다르게 이해했어요]
→ 재계획: 확인된 범위·세부 내용·철거 여부에 맞춰 다음 할 일을 판단
→ 기록 탭: "임대인 답변을 알려주셨어요"(원문은 다시 보여주지 않음)
```

> **정함(2026-11-03) — 항목 목록:** 시안의 "철거: … / 그대로: …" 항목 목록과 "할 일 3개 추가"는 만들지 않습니다. AI는 원상복구를 **범위(전부/일부)·철거 필요 여부 두 값과 자유 글(`restoration_scope_detail`)** 로 이해하고, 화면은 그 값을 "이해한 내용"으로 보여줍니다. 할 일은 로드맵의 정해진 목록이 열리는 방식입니다.
>
> **구현 확인(2026-11-07):** 선택형 입력과 직접 입력은 #197, 실패 뒤 같은 선택값 재시도는 #202, 부분 범위의 세부 질문·중복 방지는 #218에 반영됐습니다. 모름은 기존 확정값을 지우는 불필요 답변으로 취급하지 않습니다. 직접 쓴 글의 AI 검수도 유지합니다.
>
> **정함(2026-11-03) — 확인 단계:** 판단 결과는 서버가 바로 반영하고, 화면은 "이렇게 이해하고 반영했어요"와 [맞아요 / 다르게 이해했어요]를 보여줍니다(#142). 다르게 이해했으면 바로잡아 다시 적고, 이미 반영한 값과 다르면 충돌 확인(Turn 4)으로 사장님이 고릅니다. 반영 전에 멈추는 BE 확인 대기는 DB 변경 부담 때문에 발표 뒤로 미룹니다.
>
> **정함(2026-11-03) — 철거 전 준비:** 사전 신청 순서는 강제하지 않습니다(공고상 철거 뒤에도 신청 가능). 대신 AI가 철거를 권할 때 **철거 전 사진·사업자등록 업체·전자세금계산서·계좌이체** 준비를 근거와 함께 조건부로 안내합니다. 지원 자격·금액·현재 접수 가능 여부나 철거 실행은 단정하지 않습니다.
>
> - **안내 코드(#155):** 실제 모델 최종 실행(모델 호출 3회)에서 Review PASS까지 확인했습니다.
> - **공고 자료(#141, 반영됨):** 점포철거비 2026-08-03 2차 수정공고 원문을 검수 자료에 넣어 철거 작업(`PERFORM_RESTORATION`)에 연결했습니다. 이 자료는 **철거 전 증빙 준비 안내에만** 쓰고, 현재 신청 가능 여부·지원 자격·금액 판단에는 쓰지 않습니다(2026년 접수는 10-21 마감). 자료 버전이 바뀌었으므로 배포 때 기존 Case는 재적재 CLI를 실행해야 새 자료를 찾습니다.

### Turn 3 — 서류 올리기 → 점검 → 재계획

```
입력: 정산 서류(철거공사내역서·전자세금계산서·이체확인증·철거 전후 사진) + 폐업사실증명원
     (통장 사본은 공고 정산 서류 목록에 없음 — §10. 공고의 카드 결제 대체 서류는 현재 Tool에서 지원하지 않아 시연은 계좌이체 경로로 제한)
→ 문서 Tool: 종류별로 나눔 → 값 꺼냄 → 필요한 서류 확인 → 서류끼리 금액·날짜 비교
→ "이체확인증이 빠졌어요" → 사장님이 추가 → 다시 점검 → 제출 파일(ZIP) 생성
→ 누락·금액 대조는 점검 결과를 화면에 바로 보여줌(이 대조만으로는 재계획을 다시 돌리지 않음)
```

> **현재 코드(2026-11-07) — 서류로 다시 판단하기:**
>
> - **서류 API(#159, 반영됨):** 올리기·확인·빼기·점검·제출 파일(ZIP)이 서버에서 돕니다. 누락·금액 대조는 여기서 끝납니다.
> - **재판단 입력(#137, 반영됨):** 사장님이 확인한 원상복구 조항이 새로 생기거나 바뀔 때만 `DOCUMENT_SUBMITTED` 판단 입력을 만듭니다(같은 조항 재업로드·금액 서류만 추가·서류 빼기는 판단을 부르지 않음). 실제 모델 1건에서 원상복구 범위·철거 필요 여부가 채워지고 다음 판단이 "범위 확인" → "진행 상태 확인"으로 넘어가는 것을 확인했습니다. 여러 사례의 판단 정확도는 검증하지 않았습니다.
> - **BE 연결(#173, 반영됨):** 업로드·확인 뒤 `queue_document_judgment`가 아직 판단하지 않은 원상복구 조항을 확인하고, 응답 뒤 백그라운드에서 판단을 실행합니다. 홈은 PENDING 상태를 조회해 기다립니다. 현재 Context와 마지막 판단 Context를 비교하므로 같은 조항을 다시 올려 중복 판단하지 않습니다. 전체 브라우저 검증은 #232, 실제 배포 시연은 #240에서 별도로 확인합니다.

### Turn 4 — 기존 값과 다른 답 (보조 장면)

```
기존: 원상복구 범위 = 전부
새 입력: "카운터·싱크대만 빼면 된대요"
→ result: CONFLICT → Case 미변경 → 사용자 확인 화면
→ 사장님이 새 값 확인 → 재계획·필수 Review → 저장
```

실제 사례에서 임대인 번복은 확인되지 않아, 이 장면은 대표 이야기가 아니라 안전장치 검증용입니다.

## 6. Golden Case — 최소 7개

| # | 시나리오 | 검증하는 것 |
|---|---|---|
| 1 | 개인 카페 + 임차 + 원상복구 범위 모름 | 로드맵 생성 + 첫 Next Action(임대인 확인) |
| 2 | 임대인 답변으로 원상복구 범위·철거 필요 여부가 정해짐 | 값 반영 → "이렇게 이해했어요" 확인 → 재계획 후 다른 Next Action |
| 3 | 기존 값과 다른 임대인 답변 | `CONFLICT` → 사용자 확인 흐름 |
| 4 | "아직 안 정해졌대요" | 값을 바꾸지 않고 확인 질문 유지 |
| 5 | 정산 서류 중 이체확인증 누락 | 누락 안내 → 추가 후 점검 완료 → 제출 파일 |
| 6 | 상태 반영 과정에서 재계획 실패 | 결과 `FAILED`와 복구 안내(`recovery_action_code`), 이전 판단을 새 판단인 것처럼 보여주지 않음 |
| 7 | 사장님이 체크·서류를 올렸지만 기관 처리는 진행 중 | 체크·업로드만으로 공식 절차 완료·제출 완료를 만들지 않음 |

## 7. 성공지표

| 지표 | 측정 방법 |
|---|---|
| 같은 Case의 Loop 2회전 이상 | 최초 판단을 제외하고 결과 제출→실제 상태 변경→다음 행동 판단 성공을 1회로 센다. 기간을 지정한 저장 이력 조회는 #235에서 추적하며 모델 호출 수로 대신 세지 않는다 |
| Next Action 실행 가능성 | 사장님이 누구에게 무엇을 확인할지 자기 말로 다시 설명할 수 있는지 |
| 의미 있는 상태 변경 | 확인된 변경이 실제 Case 갱신으로 이어졌는지 |
| Next Action 적절성 | 재계획 후 이전과 다른, 지금 상황에 맞는 할 일이 나왔는지 |
| 서류 누락 검출 | Golden Case 5의 누락을 놓치지 않는지 |
| 명백히 틀린 Next Action | Golden Case·전문가 검토에서 0건 |
| 확정적 위험 답변 | 법률·세무·지원 자격 단정 0건 |
| 전문용어 혼란 | 세션당 사용자 되물음 2회 이하 |

## 8. 스코프 리마인더

- 폐업 날짜는 사장님이 고른 값을 그대로 씁니다 — **AI는 최적 폐업일을 추천하지 않습니다.**
- 점포철거비 등 지원금은 자격을 확정하지 않습니다. **신청·제출은 사장님이 소상공인24에서 직접** 하고, 서비스는 준비와 기록만 돕습니다. 금액은 공고상 상한이고 예산이 떨어지면 접수가 끝나므로, "받을 수 있어요" 대신 "공고 조건에 맞는지 소상공인24에서 확인하세요"라고 씁니다.
- 부가세 폐업 신고 기한은 폐업일 기준이라 가게 반환·보증금 정산보다 먼저 올 수 있습니다. 순서도에서 맨 끝에 있어도 기한은 공식 근거를 붙여 따로 안내해야 합니다(아직 구현 전).
- 직원이 있으면 해고예고(30일)를 폐업 준비 단계에서 챙겨야 합니다. 로드맵 "직원에게 폐업 알리기"에 근로기준법 제26조를 검수한 근거와 함께 설명을 붙입니다(#144).
- 폐업 시기는 상황 진단에서 [이번 달 안에 / 다음 달 / 아직 안 정했어요] 중에서 받습니다(#156). 앞의 둘은 예상 달(`planned_closure_month`)로 보내고 확정된 날짜로 다루지 않습니다. 날짜와 예상 달을 둘 다 보내면 BE가 거절합니다(#145).
- 기존 값과 다른 입력은 자동으로 한쪽을 고르지 않습니다 — 항상 사장님 확인을 거칩니다.
- 체크리스트 완료는 사장님의 보고이며, 기관 승인이나 절차 완료를 뜻하지 않습니다.
- 세금·지원금의 기한과 금액은 서비스가 계산해서 단정하지 않습니다.

전체 스코프 제외 목록은 `/CLAUDE.md`를 참고하세요.
