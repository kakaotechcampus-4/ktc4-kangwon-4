# RE:BORN Hero Scenario

> 사용자 시나리오와 Hero Loop 상세 흐름입니다. **기준은 2026-10-30 팀이 확정한 v3 모바일 프로토타입(봄날 개인카페 시연)** 입니다. 이전판(2026-09-28)의 "인수자 대기·임대인 번복" 이야기는 실제 사례가 확인되지 않아 대표 장면에서 뺐습니다(§9).
> Agent·Tool 책임은 `docs/agent/architecture.md`를 참고합니다. BE와의 계약은 FastAPI 코드와 `backend/app/agent/schemas.py`가 기준입니다.

## 1. 한 줄 소개

폐업 준비부터 제출까지, 가게 상황이 바뀔 때마다 다음 할 일 하나를 다시 계산해 주는 서비스.

## 2. 타깃 페르소나

폐업 의사는 이미 확정했지만 임대차·원상복구·철거·지원금·신고·세무를 스스로 챙겨야 하는 **1~5인 비프랜차이즈 개인 카페 사장님**(가게를 빌려 쓰는 경우).
현재 로드맵은 개인 카페만 지원합니다. 프랜차이즈 카페와 일반 음식점은 "지원 준비 중"으로 안내합니다.

## 3. 대표 Hero Case — 봄날 개인카페

> 봄날 개인카페 사장님이 버튼으로 가게 상황(빌린 가게·직원·대출·배달앱 계약, 계약서의 원상복구 조항, 폐업 날짜)을 고르면 5단계 폐업 순서가 만들어지고, 첫 할 일로 "임대인에게 원상복구 범위 확인하기"가 나온다.
> 사장님이 임대인 답변("카운터랑 싱크대는 빼고, 간판도 떼야 한대요. 바닥 타일은 그대로 둬도 된대요")을 알려주면, AI가 이해한 내용을 보여주고 사장님이 맞다고 확인한 뒤 할 일이 다시 계산된다.
> 이후 점포철거비 사전 신청 → 1차 적격심사 결과 → 영업 마무리 → 철거 → 폐업 신고(원스톱) → 정산 서류 점검·제출 → 가게 반환 → 부가세 신고까지 같은 방식으로 이어진다.

점포철거비는 **철거 전에 신청**해야 하고, 사장님이 직접 철거하면 지원 대상이 아닙니다. 정산 서류를 내려면 폐업 신고가 먼저 끝나 있어야 합니다(희망리턴패키지 2026 공고 기준, §10). 카운터·싱크대를 떼면 영업을 계속할 수 없으므로 영업 마무리가 철거보다 먼저입니다.

실제 사례에서 반복되는 패턴은 "원상복구 범위가 처음엔 정해지지 않고, 임대인 요구가 조금씩 추가된다"입니다(2026-10-11 사례 리서치). 이 시나리오는 그 패턴을 따릅니다.

## 4. Hero Loop — 7단계

| 단계 | 시스템이 해야 할 일 |
|---|---|
| 1. 입력 | 사장님이 **버튼·체크·날짜·서류 첨부**로 상황을 알려준다. 자연어는 임대인 답변 한 곳에서만 받는다. |
| 2. 사실 추출 | 정보분석 Agent가 입력에 있는 값만 꺼내고 근거를 붙인다. 서류는 문서 Tool이 종류를 나누고 값을 꺼낸다. |
| 3. Case 인식 | 저장된 값·진행 상태로 5단계 로드맵의 각 할 일이 해당/해당 없음/확인 필요인지 정하고 Blocker를 찾는다. |
| 4. 계획 | Supervisor가 Next Action 1개와 이유를 만들고 필수 Review를 거친다. 로드맵은 이 할 일을 해당 칸에 연결해 보여준다. |
| 5. 현실 실행 | 사장님이 임대인 연락·소상공인24 신청·업체 계약·신고를 직접 한다. |
| 6. 결과 입력 | "다 알렸어요", "신청했어요" 같은 버튼, 임대인 답변, 서류 올리기로 결과를 알려준다. |
| 7. 검증·재계획 | 기존 값과 다르면 사장님에게 되묻고, 확인된 결과로 계획 전체를 다시 검토한다. |

`/CLAUDE.md`의 축약된 Hero Loop("Case 생성 → Blocker 1개 판단 → Next Action 1개 제시 → 사용자 실행 → 결과 입력 → Case 상태 변경 → 재계획 → 반복")의 상세판입니다.

## 5. Turn-by-turn 워크스루

### Turn 1 — 상황 진단 → 로드맵과 첫 할 일

```
입력(버튼): 가게를 빌려 씀, 직원 있음, 계약서에 원상복구 조항 있음, 폐업 날짜
→ 5단계 로드맵 생성(폐업 준비 / 원상복구·철거 / 영업 마무리·폐업 신고 / 지원금 정산·가게 반환 / 세금·마무리)
→ 원상복구 범위 = 모름
→ Next Action: "임대인에게 원상복구 범위와 철거 필요 여부를 확인하세요."
→ 화면: "임대인에게 이 두 가지만 물어보세요" 질문 목록
```

### Turn 2 — 임대인 답변 → AI 이해 확인 → 재계획 (시연 핵심)

```
입력: 보기 3개(전부 원래대로 / 카운터·싱크대만 빼면 됨 / 아직 안 정해짐) 또는 직접 쓰기
직접 쓴 예: "카운터랑 싱크대는 빼고, 간판도 떼야 한대요. 바닥 타일은 그대로 둬도 된대요."
→ 정보분석 Agent: 문장에 있는 값만 변경 후보로 꺼냄(원상복구 범위 = 일부, 철거 = 필요)
→ 화면: "이렇게 이해했어요" → 사장님이 [맞아요 / 다시 쓸게요]
→ 확인되면 재계획: 점포철거비 조건 확인·사전 신청이 다음 할 일로 열림 (철거보다 먼저)
→ 기록 탭: "임대인 답변을 알려주셨어요"(원문은 다시 보여주지 않음)
```

> **결정 대기 1 — 항목 목록:** 시안은 "철거: 카운터·싱크대·간판 / 그대로: 바닥 타일"처럼 **항목 목록**을 보여주고 "답변대로 할 일 3개를 추가"합니다. 현재 AI는 원상복구를 **범위(전부/일부)와 철거 필요 여부 두 값**과 자유 글 칸(`restoration_scope_detail`)으로 이해하고, 로드맵 할 일은 정해진 목록입니다. 항목 목록을 AI에 추가할지, 두 값 + 자유 글로 화면을 맞출지 팀 결정이 필요합니다.
>
> **결정 대기 2 — 확인 단계:** 현재 화면은 답변을 보내면 AI 판단 결과를 바로 반영하고 "말씀하신 내용을 반영했어요"를 보여줍니다. 사장님 확인 화면은 기존 값과 충돌할 때만 나옵니다. "이렇게 이해했어요 → 맞아요"를 모든 답변에 넣을지 FE·BE 결정이 필요합니다.
>
> **결정 대기 3 — 사전 신청 순서:** 지금 AI가 다음 할 일로 고를 수 있는 공식 절차 8개에는 점포철거비 신청이 없고, 사전 신청은 사장님 체크 항목입니다. 범위 확인 뒤 AI가 철거 작업을 먼저 권하지 않도록 절차 자료나 로드맵 순서를 맞춰야 합니다.

### Turn 3 — 서류 올리기 → 점검 → 재계획

```
입력: 정산 서류(철거공사내역서·전자세금계산서·이체확인증·철거 전후 사진) + 폐업사실증명원
     (통장 사본은 공고 원문 확인 전까지 "확인 필요" — §10)
→ 문서 Tool: 종류별로 나눔 → 값 꺼냄 → 필요한 서류 확인 → 서류끼리 금액·날짜 비교
→ "이체확인증이 빠졌어요" → 사장님이 추가 → 다시 점검 → 제출 파일(ZIP) 생성
→ 서류에서 새로 알게 된 값은 사장님 입력과 같은 길로 재계획에 들어감(기존 값을 바로 덮지 않음)
```

### Turn 4 — 기존 값과 다른 답 (보조 장면)

```
기존: 원상복구 범위 = 전부
새 입력: "카운터·싱크대만 빼면 된대요"
→ result: CONFLICT → Case 미변경 → 사용자 확인 화면
→ 사장님이 새 값 확인 → 재계획·필수 Review → 저장
```

실제 사례에서 임대인 번복은 확인되지 않아, 이 장면은 대표 이야기가 아니라 안전장치 검증용입니다.

## 6. Golden Case — 최소 7개

| # | 시나리오 | 검증하는 것 |
|---|---|---|
| 1 | 개인 카페 + 임차 + 원상복구 범위 모름 | 로드맵 생성 + 첫 Next Action(임대인 확인) |
| 2 | 임대인 답변으로 원상복구 범위·철거 필요 여부가 정해짐 | 변경 후보 → 사장님 확인 → 재계획 후 다른 Next Action |
| 3 | 기존 값과 다른 임대인 답변 | `CONFLICT` → 사용자 확인 흐름 |
| 4 | "아직 안 정해졌대요" | 값을 바꾸지 않고 확인 질문 유지 |
| 5 | 정산 서류 중 이체확인증 누락 | 누락 안내 → 추가 후 점검 완료 → 제출 파일 |
| 6 | 상태 반영 과정에서 재계획 실패 | `REPLAN_FAILED`, 이전 판단을 새 판단인 것처럼 보여주지 않음 |
| 7 | 사장님이 체크·서류를 올렸지만 기관 처리는 진행 중 | 체크·업로드만으로 공식 절차 완료·제출 완료를 만들지 않음 |

## 7. 성공지표

| 지표 | 측정 방법 |
|---|---|
| 세션당 Loop 2회전 이상 | 저장된 재계획 완료 이력과 Langfuse trace로 집계 |
| Next Action 실행 가능성 | 사장님이 누구에게 무엇을 확인할지 자기 말로 다시 설명할 수 있는지 |
| 의미 있는 상태 변경 | 확인된 변경이 실제 Case 갱신으로 이어졌는지 |
| Next Action 적절성 | 재계획 후 이전과 다른, 지금 상황에 맞는 할 일이 나왔는지 |
| 서류 누락 검출 | Golden Case 5의 누락을 놓치지 않는지 |
| 명백히 틀린 Next Action | Golden Case·전문가 검토에서 0건 |
| 확정적 위험 답변 | 법률·세무·지원 자격 단정 0건 |
| 전문용어 혼란 | 세션당 사용자 되물음 2회 이하 |

## 8. 스코프 리마인더

- 폐업 날짜는 사장님이 고른 값을 그대로 씁니다 — **AI는 최적 폐업일을 추천하지 않습니다.**
- 점포철거비 등 지원금은 자격을 확정하지 않습니다. **신청·제출은 사장님이 소상공인24에서 직접** 하고, 서비스는 준비와 기록만 돕습니다. 금액은 공고상 상한이고 예산이 떨어지면 접수가 끝나므로, "받을 수 있어요" 대신 "공고 조건에 맞는지 소상공인24에서 확인하세요"라고 씁니다.
- 부가세 폐업 신고 기한은 폐업일 기준이라 가게 반환·보증금 정산보다 먼저 올 수 있습니다. 순서도에서 맨 끝에 있어도 기한은 따로 안내합니다.
- 직원이 있으면 해고예고(30일)를 폐업 준비 단계에서 챙겨야 합니다. 로드맵에 넣을지는 결정 대기입니다.
- 기존 값과 다른 입력은 자동으로 한쪽을 고르지 않습니다 — 항상 사장님 확인을 거칩니다.
- 체크리스트 완료는 사장님의 보고이며, 기관 승인이나 절차 완료를 뜻하지 않습니다.
- 세금·지원금의 기한과 금액은 서비스가 계산해서 단정하지 않습니다.

전체 스코프 제외 목록은 `/CLAUDE.md`를 참고하세요.
